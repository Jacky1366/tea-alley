# Decision log

Deliberate deviations from the Development Plan (`docs/development-plan.md`), and other decisions worth keeping. Where this log differs from the plan, this log wins.

| Date | Ticket | Decision | Reason |
| --- | --- | --- | --- |
| 2026-11-14 | T2-5 (#38) | Checkout doesn't restrict payment methods in code; the Stripe Dashboard decides (Cards only for the demo). The webhook also marks an order paid on `checkout.session.async_payment_succeeded`. | Stripe API version 2026-10-28 (stripe-php v23) rejects `payment_method_types`. Without card-only in code, a delayed method could complete "unpaid" and be paid later, so that event must be handled. |
| 2026-11-14 | T2-5 (#38) | A drink sold out (86'd) after the order was placed doesn't stop the payment: the webhook marks the order paid. | The order was validated, priced, and snapshotted when it was placed, and the customer paid that snapshot total. The webhook checks the amount against the order, never the current menu. Staff handle an unavailable drink at the counter. |
| 2026-11-14 | T2-5 (#38) | `orders:cancel-stale` cancels a pending order only 5 minutes after its current Checkout Session expires (`orders.payment_expires_at`), not 30 minutes after the order was placed. | A retry starts a fresh Session, so the order's age would cancel an order the customer is paying for right now. An order with no Session uses its creation time plus 30 minutes. |
| 2026-11-14 | T2-5 (#38) | Checkout Sessions expire after 31 minutes, not 30. | Stripe requires at least 30 minutes after the Session is created; 30 computed by the app can arrive a moment short and be rejected. |
| 2026-11-14 | T2-5 (#38) | The cart is emptied as soon as the order is placed, not when it's paid. | Paying (and retrying) happens on the order's own page; with Stripe the order is never paid during checkout. |
| 2026-11-14 | T2-5 (#38) | The barista board's Ready column shows ready orders from any day, oldest first. Paid and Preparing still show today only. | A drink nobody collected shouldn't vanish from the board at midnight. |
| 2026-11-14 | T2-6 (#32) | The order-ready notification is email only. There is no database-channel notification. | T2-4's live status page already flips to Ready the moment the barista bumps, so an in-app notice would duplicate it. |
| 2026-11-16 | T2-7 | **Promo codes are deferred, not cancelled**, until there's free time after exam prep. The `promo_codes` table from T1-1 stays as it is, and there's no promo UI for customers or in Filament. If resumed, the agreed design (which replaces the plan's T2-7 bullets) is: (1) a use is reserved when the order is placed: the count is the orders using the code that aren't cancelled, derived from `orders`, with the promo row locked by `lockForUpdate` in `OrderService::place()`, not a `used_count` bumped by the webhook; (2) one use per customer; (3) one generic error ("invalid or expired") for every failure, plus rate limiting on validation; (4) percent in basis points, fixed amount in cents, through `PricingService`'s existing allocation across lines and its clamp at the subtotal; (5) Stripe gets the discounted total as the single line item; (6) a used promo can be deactivated but not deleted; (7) the code is re-validated inside the placement transaction. Resuming needs a new migration: `value` is documented as a 1-100 percent, and `used_count` would no longer be used. | Exam prep comes first. Counting from orders at placement can't drift from the orders themselves, and it stops two customers both using the last use while their payments are pending. |
| 2026-11-16 | T2-8 (#47) | The audit log covers `MenuItem` and `ModifierOption` only, not `PromoCode`. | T2-7 promo codes are deferred (#45). Add `PromoCode` to the observer when T2-7 resumes. |
| 2026-11-16 | T2-8 (#47) | Deleting a modifier group now deletes its options one by one through Eloquent (in one transaction) before the group. | The foreign key's `ON DELETE CASCADE` removes rows without model events, so the options' deletions would be missing from the audit log. |
| 2026-11-16 | T2-8 (#47) | Not audited: creates (the plan asks for update / delete), and which modifier groups a drink has (the `menu_item_modifier_group` pivot). Audit log entries can't be edited or deleted through the app. | The pivot isn't a column of either audited model. An audit log that could be edited couldn't be trusted. |
| 2026-11-16 | T2-9 (#47) | Dashboard "sales" means subtotal minus discount, before tax. The amount collected including GST and PST is shown next to it. | Sales tax is collected for the government, not earned. Both figures are sums of amounts `PricingService` already stored; the dashboard calculates nothing that is stored or charged. |
| 2026-11-16 | T2-9 (#47) | An order counts on the Vancouver day it was **paid** (`paid_at`), not the day it was placed. The "this week" trend is the last 7 days (today and the 6 before), not Monday to Sunday. | Paid is when it became a sale; an order placed at 23:58 and paid at 00:01 is the next day's sale. A rolling 7 days always shows a full week of bars. |
| 2026-11-16 | T2-9 (#47) | Best sellers, sugar levels, toppings, and the menu's "Most popular" sort all use the last 30 Vancouver days. The dashboard groups drinks by their snapshot name; the menu sort counts by `menu_item_id`. | One window keeps the dashboard and the menu consistent. Snapshot names keep a deleted drink's history, and `menu_item_id` keeps a renamed drink's popularity. |
| 2026-11-16 | T2-9 (#47) | Filament's default "Filament info" widget is removed from the dashboard. | It's a Filament promotion, not shop data. |
